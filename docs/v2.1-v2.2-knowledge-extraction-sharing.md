# AITestCraft 技术分享：从历史用例提取知识库到智能生成测试用例

## 一、背景与问题

AITestCraft 的核心能力是**正向生成**测试用例：`需求文档 → 测试点提取 → 用例生成 → 评审补全`。但在实际业务中，测试团队往往已经积累了大量历史用例，这些用例中蕴含着丰富的产品需求知识——功能点、业务规则、边界条件、异常场景。

**核心问题**：
- 新需求生成用例时，无法参考历史用例中的业务规则和边界条件，导致生成的用例缺乏业务深度
- 历史用例中的知识没有被结构化沉淀，每次都要从零开始理解业务
- 用例平台上有大量已有用例，但 AI 无法直接利用这些"知识资产"

**解决思路**：
1. **逆向提取**：从历史用例中逆向归纳出结构化的需求知识点，沉淀为知识库
2. **正向复用**：在生成新用例时，将知识库作为上下文注入，让 AI 参考历史知识生成更准确的用例
3. **平台打通**：在用例平台 AgileTC 上增加知识库提取入口和知识库选择功能，形成完整闭环

## 二、整体架构

### 2.1 双工作流并行架构

系统设计了两个并行的工作流，共享同一套基础设施（任务调度、断点恢复、Token 统计、日志系统）：

```
├────────────────────────────────┬─────────────────────────────────┤
│   知识提取工作流 (v2.1)        │   用例生成工作流 (v1.0+)        │
│                                │                                 │
│  fetch-cases (代码)            │  requirement-parser             │
│     → summarize-modules        │     → testpoint-extractor      │
│     → dedup-knowledge          │     → testcase-generator       │
│     → resolve-conflicts        │     → testcase-reviewer        │
│     → consolidate-knowledge    │     → coverage-analysis        │

│         知识库提取入口 ←→ 知识库选择 → 用例生成                    │

```

## 三、知识提取工作流（Knowledge Extraction）

### 3.1 工作流节点设计

知识提取工作流共 4 个 LLM 节点（fetch-cases 由代码完成，不纳入工作流）：

| 节点 | 职责 | 输入 | 输出 | 输出格式 |
|------|------|------|------|----------|
| **fetch-cases** | 调用外部 API 获取用例 | 用例 ID 列表 | 标准化用例 JSON | 代码执行 |
| **summarize-modules** | 按模块归纳需求知识点 | 标准化用例数组 | 各模块知识 Markdown | json |
| **dedup-knowledge** | 全局语义去重 | 模块知识 Markdown | 去重后知识点数组 | json |
| **resolve-conflicts** | 冲突检测与解决 | 去重后知识点数组 | 冲突解决后数组 | json |
| **consolidate-knowledge** | 汇总格式化并持久化 | 冲突解决后数组 | Markdown + JSON | mixed |

**执行顺序**：
```
summarize-modules → dedup-knowledge → resolve-conflicts → consolidate-knowledge
```

### 3.2 fetch-cases：树形用例解析

**核心挑战**：AgileTC 用例平台返回的是树形嵌套结构（KityMinder 脑图格式），不是扁平的表格数据。

**原始数据结构**：
```json
{
  "code": 200,
  "data": {
    "categoryName": "手机号登录",
    "caseContent": {
      "root": {
        "data": { "text": "手机号登录" },
        "children": [
          {
            "data": { "text": "[P0] TC001: 验证码登录-登录成功" },
            "children": [
              { "data": { "resource": ["前置条件"], "text": "用户未登录" } },
              { "data": { "resource": ["执行步骤"], "text": "1. 打开登录页面" },
                "children": [
                  { "data": { "resource": ["执行步骤"], "text": "2. 输入手机号" } }
                ]
              },
              { "data": { "resource": ["预期结果"], "text": "登录成功" } }
            ]
          }
        ]
      }
    }
  }
}
```

**解析规则**（`utils/case_parser.py`）：

1. **根节点** `root.data.text` → 模块名（如「手机号登录」）
2. **第一层子节点** → 单个用例，标题格式 `[P0] TC001: 场景-预期`
3. **resource 字段**区分节点类型：`前置条件` / `执行步骤` / `预期结果`
4. **步骤链式结构**：执行步骤通过 `children` 链式嵌套，需递归展开

**标准化输出**：
```json
[{
  "case_id": "TC001",
  "module": "手机号登录",
  "priority": "P0",
  "name": "验证码登录-登录成功",
  "precondition": "用户未登录",
  "steps": ["打开登录页面", "输入手机号"],
  "assert": ["登录成功"]
}]
```

**为什么 fetch-cases 不用 LLM**：LLM 无法调用外部 HTTP API，获取用例数据必须通过代码完成。工作流从 `summarize-modules` 节点开始。

### 3.3 summarize-modules：按模块归纳知识

接收标准化用例数组，按模块归纳为四类需求知识点：

| 维度 | 说明 | 示例 |
|------|------|------|
| 功能点 | 核心功能、用户行为 | 手机号验证码登录、密码登录 |
| 业务规则 | 约束条件、校验规则 | 验证码有效期10分钟、同手机号发送间隔60秒 |
| 边界条件 | 最大值、最小值、临界值 | 验证码刚好过期、手机号带+86前缀 |
| 异常场景 | 错误输入、异常流程 | 验证码错误、网络异常 |

**关键设计**：每条知识点必须标注来源用例 ID，为后续冲突解决提供依据。

### 3.4 dedup-knowledge：全局语义去重

不同模块中可能存在语义重复的知识点，去重规则：

1. **重复**：场景相同 + 行为相同 + 断言目标一致 → 合并
2. **相似**：「验证码为6位数字」和「验证码必须是6位数字」→ 合并，保留描述最完整的版本
3. **保留**：不同模块中相似但上下文不同 → 保留（如登录的「密码错误」和修改密码的「密码错误」）

### 3.5 resolve-conflicts：冲突解决

当不同用例对同一场景描述矛盾时（如 TC001 说验证码有效期5分钟，TC005 说10分钟）：

**解决规则**：**用例 ID 大的代表新版本，优先采纳**

```json
// 被覆盖的旧版本
{
  "content": "验证码有效期 5 分钟",
  "source_case_ids": ["TC001"],
  "status": "changed",
  "old_content": "验证码有效期 5 分钟",
  "change_reason": "用例 TC005 覆盖：需求更新为 10 分钟"
}

// 采纳的新版本
{
  "content": "验证码有效期 10 分钟",
  "source_case_ids": ["TC005"],
  "status": "active"
}
```

### 3.6 consolidate-knowledge：汇总持久化

将知识点汇总为 Markdown + JSON 双格式，并持久化到数据库：

- `knowledge_bases` 表：知识库主记录（标题、模块列表、源用例 ID、内容哈希）
- `knowledge_items` 表：知识点明细（模块、类型、内容、优先级、来源用例、状态、变更历史）

## 四、知识库增量更新

### 4.1 智能跳过：无变更不重复提取

提交知识提取任务时，系统首先检查是否已有对应知识库：

1. **按 categoryName 查找**：同一分类下的用例归入同一知识库
2. **按用例 ID 查找**：回退匹配，确保不遗漏

```python
# 如果用例已提取且无变更 → 直接返回已有知识库
if existing_kb and not changed_cases:
    return { "skipped": True, "knowledge_base_id": existing_kb["id"] }
```

### 4.2 内容哈希：精准检测变更

通过 MD5 哈希对比用例内容，精准检测哪些用例发生了变更：

```python
# 获取用例内容 → 计算哈希 → 对比已有哈希
content_hash = hashlib.md5(json.dumps(case_content, sort_keys=True).encode()).hexdigest()
if current_hash != stored_hash:
    changed_cases.append(case_id)
```

### 4.3 增量合并：只处理变更部分

```
已提取的用例 [TC001, TC002, TC003]
  + 新提交 [TC002(已修改), TC004(新增)]
  = 只对 TC002, TC004 走提取流程
  = 增量合并到已有知识库
```

合并策略：
- 按模块+内容哈希建立索引
- 新旧知识点匹配时，按用例 ID 判断版本，大的优先
- 未被新知识匹配的旧知识保留不变

## 五、用例生成时的知识库注入

### 5.1 /run 接口扩展

用例生成接口新增 `knowledge_base_id` 可选参数：

```http
POST /api/run
Content-Type: multipart/form-data

task=用户登录功能需求...
knowledge_base_id=kb_abc123
caseId=12345
```

### 5.2 知识库上下文注入

当提供 `knowledge_base_id` 时，系统自动将知识库内容构建为上下文，附加到需求前面：

```python
def _build_knowledge_context(kb: dict, items: list) -> str:
    lines = ["## 知识库上下文\n"]
    if kb.get("title"):
        lines.append(f"### {kb['title']}\n")
    lines.append("### 需求知识点：\n")
    for item in items:
        lines.append(f"- [{item['module']}] {item['item_type']}: {item['content']}\n")
    return "\n".join(lines)
```

**注入效果**：AI 在解析新需求时，会看到历史用例中归纳出的知识点，生成的测试用例会更加准确和完整。

```python
# 最终输入 = 知识库上下文 + 新需求
if kb_context:
    task_with_context = f"{kb_context}\n\n---\n\n## 新需求\n\n{task}"
```

### 5.3 生成效果对比

| 场景 | 无知识库 | 有知识库 |
|------|---------|---------|
| 业务规则 | 需要从需求文档推断，可能遗漏 | 直接参考历史归纳的规则，如"验证码有效期10分钟" |
| 边界条件 | 依赖 AI 常识，不够精准 | 参考历史用例的边界值，如"手机号11位" |
| 异常场景 | 覆盖基本异常 | 参考历史测试的异常场景，如"SQL注入防护"、"并发登录" |
| 一致性 | 不同人/不同时间可能不同 | 与历史用例风格保持一致 |

## 八、关键技术决策

### 8.1 为什么 fetch-cases 用代码而不用 LLM

LLM 无法调用外部 HTTP API，获取用例数据必须在代码层完成。这一决策带来的好处：
- **可靠性**：API 调用和解析由代码保证，不受 LLM 幻觉影响
- **性能**：并发获取 + 树形解析，速度远快于 LLM 处理
- **成本**：减少一次 LLM 调用，节省 Token 消耗

### 8.2 为什么用内容哈希而非时间戳检测变更

- 时间戳可能因数据迁移、系统升级等原因不可靠
- 内容哈希直接反映用例实际内容是否变化
- 即使用例被"保存但未修改"，哈希不变，不会触发无意义的重提取

### 8.3 为什么 consolidate-knowledge 输出 mixed 格式

知识库需要同时满足两种使用场景：
- **人类阅读**：Markdown 格式，按模块分组，包含变更历史
- **机器使用**：JSON 格式，结构化知识点，用于注入 AI 上下文

`mixed` 格式用 `---` 分隔 Markdown 和 JSON 部分，Node 层自动拆分和解析。

### 8.4 为什么冲突解决用用例 ID 而非时间戳

- 用例 ID 本身包含版本信息（TC005 > TC001 表示 TC005 是更新后的用例）
- 不依赖外部时间戳，避免了时区、精度等问题
- 规则简单明确，LLM 和代码都能一致执行

## 十、端到端流程演示

### 场景：为「手机号登录」新需求生成测试用例

**Step 1：从历史用例提取知识库**

```bash
curl -X POST http://localhost:8001/api/knowledge/extract \
  -H "Content-Type: application/json" \
  -d '{"case_ids": ["TC001", "TC002", "TC005"]}'
```

响应：
```json
{ "task_id": "550e8400-...", "skipped": false, "mode": "full" }
```

**Step 2：查看知识库**

```bash
curl http://localhost:8001/api/knowledge/bases/kb_550e8400
```

响应包含知识点：
- [手机号登录] rule: 验证码有效期10分钟
- [手机号登录] boundary: 手机号必须为11位
- [手机号登录] exception: 连续5次密码错误锁定账号
- ...

**Step 3：关联知识库生成新用例**

```bash
curl -X POST http://localhost:8001/api/run \
  -F "task=新增微信快捷登录功能需求..." \
  -F "knowledge_base_id=kb_550e8400" \
  -F "caseId=12345"
```

AI 在生成用例时会参考知识库中的「手机号登录」相关知识点，确保新用例与历史测试风格一致、边界条件覆盖全面。

**Step 4：用例自动回写到 AgileTC**

任务完成后，KityMinder 格式的用例自动回写到用例平台，无需人工操作。

## 十一、总结

本次改动的核心价值在于**将历史用例从"死数据"转化为"活知识"**：

1. **逆向提取**：历史用例 → 结构化知识库，沉淀业务规则和边界条件
